> 참조 문서: [백엔드 설계](../architecture/backend/README.md), [도메인 모델](../architecture/domain.md) (구 design/mvp-service-design.md)

## 검토 요약

서비스 비전/기능/수익 모델은 잘 구성되어 있으나, 실제 설계 문서(mvp-service-design.md)와 기술 스택이 불일치하고, MVP 범위 정의가 두 문서 간 충돌하며, 운영/보안/법적 항목의 구체성이 부족했음.

---

## 잘된 점

1. **명확한 포지셔닝** — tiiny.host와의 비교 테이블이 효과적이며, "배포 이후의 수정 루프"라는 차별점이 일관되게 관통
2. **사용자 플로우 구체성** — 4개의 플로우(비로그인/AI수정/팀/CLI)가 단계별로 잘 기술되어 구현 방향이 명확
3. **수익 모델의 논리적 정합성** — AI 사용량을 과금 축으로 삼은 것이 비용 구조(Claude API 호출 비용)와 가치(AI 수정 기능)를 잘 일치시킴
4. **전환 비용 전략** — 버전 히스토리 축적, 팀 워크스페이스, 커스텀 도메인을 통한 고착화 전략이 구체적
5. **Phase별 로드맵** — 4-6주 / 7-12주 / 13주~ 로 나뉜 구현 단계가 현실적인 규모감

---

## Critical (치명적 문제)

### C-1: 기술 스택이 실제 설계 문서와 완전히 불일치

계획서는 **Next.js API Routes + Server Actions** 기반 풀스택 아키텍처를 기술하고 있으나, 실제 MVP 설계 문서는 **Spring Boot 3.x + Next.js 분리 아키텍처**로 재설계됨.

| 항목 | 계획서 (service-plan.md) | 실제 설계 (mvp-service-design.md) |
|------|---|---|
| 백엔드 | Next.js API Routes | Spring Boot 3.x REST API |
| 인증 | NextAuth.js (Auth.js v5) | Spring Security + JWT + OAuth2 |
| ORM | Drizzle ORM | Spring Data JPA |
| 배포 | Vercel 단일 | Vercel (FE) + Railway (BE) |

**권장 조치**: 섹션 3을 현재 확정된 분리 아키텍처 기준으로 전면 업데이트

### C-2: MVP 범위가 두 문서 간 충돌

계획서 MVP(Phase 1)에 AI 수정 기능, 버전 히스토리가 P1으로 포함되어 있으나, 실제 MVP 설계 문서에서는 **명시적으로 제외**됨. MVP의 정의 자체가 다른 상태.

**권장 조치**: 계획서의 MVP 범위와 주차별 일정을 mvp-service-design.md의 확정 범위에 맞춰 재조정

## Major (주요 개선사항)

### M-1: 비로그인 임시 URL 만료 시간 불일치

- 플로우 A: "24시간 후 만료"
- 수익 모델 Free 플랜: "7일 만료"
- MVP 설계 문서: "24h 만료"

**권장 조치**: 만료 정책을 하나의 테이블로 정리 (비로그인 24시간 / Free 7일 / Starter 이상 영구)

### M-2: 보안 전략이 선언적 수준에 머물러 있음

"XSS → 샌드박스 iframe, CSP 헤더"라고만 언급. `<script>` 태그 허용 여부 등 핵심 보안 결정과 근거 누락.

**권장 조치**: 리스크 섹션에 "사용자 HTML 처리 정책" 추가 — 허용 범위(script 허용/금지)와 격리 전략 핵심 원칙 기술

### M-3: AI API 비용 추정 및 손익분기점 부재

AI 사용량 과금 모델이면서 실제 API 호출 비용 추정이 없음. 플랜별 마진 판단 근거 부재.

**권장 조치**: AI 수정 1회당 예상 토큰 사용량/비용 추정, 플랜별 예상 마진 계산 섹션 추가

### M-4: 성공 지표(KPI)가 전혀 없음

"핵심 가치 검증"이 Phase 1 목표이나 검증 성공 기준 미정의.

**권장 조치**: Phase별 성공 기준 추가 (예: Phase 1 — WAU 100명, 전환율 5%)

### M-5: 경쟁 분석 범위가 좁음

벤치마킹 대상이 tiiny.host 하나뿐. Claude Artifacts가 공유 URL 기능 추가 시 존립 위협.

**권장 조치**: 경쟁 분석 확대 (CodePen, JSFiddle, GitHub Pages, Claude Artifacts 등) + LLM 제공사 직접 공유 시 방어 전략 포함

## Minor (사소한 개선사항)

### m-1: Markdown 렌더링 우선순위 낮음 (P2)

LLM 출력의 상당 부분이 Markdown인데 P2로 분류. MVP 설계 문서에서는 이미 MVP에 포함.

**권장 조치**: P0-P1로 상향 조정

### m-2: 아키텍처 다이어그램이 텍스트 기반

ASCII 형태로는 데이터 흐름 표현 부족.

**권장 조치**: Mermaid 등 활용한 시퀀스 다이어그램 추가

### m-3: CLI 도구 이름 미확정

`docshare`라는 CLI 이름이 등장하나 서비스명 자체가 미확정.

**권장 조치**: 서비스명/도메인 결정에 대한 언급 추가

## 추가 고려사항

1. **문서 버전 관리 체계** — 계획서에 "마지막 업데이트일"과 "관련 설계 문서 링크" 추가, 변경 시 동기화 프로세스 필요
2. **데이터 마이그레이션 전략** — Phase 전환 시 스키마 변경(커스텀 slug, 버전 히스토리 테이블 등)에 대한 언급 필요
3. **Rate Limiting** — 비로그인 대량 문서 생성 방지, AI API 남용 방지 전략 필요
4. **국제화(i18n)** — Phase 3에 다국어 지원이 있으나, 초기부터 i18n 라우팅을 준비해두는 것이 효율적
5. **Team 플랜 가격 근거** — $12/인/월의 마진이 팀 기능 추가 비용 대비 충분한지 검토 필요
