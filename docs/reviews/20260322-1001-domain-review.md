# domain.md 검토 결과

> 검토일: 2026-03-22
> 검토 대상: docs/architecture/domain.md
> 참조 문서: backend.md, product.md, restructure-review.md
> 검토 기준: 도메인 모델 완성도, 문서 간 중복, 논리적 일관성, 누락, 불필요 내용

---

## 요약

domain.md는 구현에 필요한 핵심 요소(엔티티, ERD, DDL, 도메인 규칙, R2 키 구조)를 잘 갖추고 있으며, 전반적으로 높은 완성도를 보인다. 치명적 문제는 없다. 주요 개선사항으로는 **id/slug 이중 컬럼의 불필요성 명확화**, **StorageUsage 동시성 제어 전략 부재**, **refresh_tokens 엔티티 정의 누락** 등이 있다. 사소한 개선사항 다수가 식별되었다.

---

## 1. 잘된 점

- **엔티티 -> ERD -> DDL 3단계 정의**: 동일한 데이터 모델을 개념(섹션 2), 관계도(섹션 4/7), 물리(섹션 8)로 일관되게 기술했다. 구현자가 각 추상화 수준에서 모델을 확인할 수 있다.
- **PENDING 상태 도입과 실패 시나리오**: 2단계 커밋 패턴(DB INSERT -> R2 업로드 -> DB UPDATE)의 각 실패 지점에 대한 대응이 domain.md(DR-9)와 backend.md(섹션 7.1)에 걸쳐 명확하게 정의되어 있다.
- **StorageUsage.documentCount 주의사항**: 캐싱 카운터의 정확성 한계를 솔직하게 명시하고, 대시보드에서는 실시간 쿼리를 사용하라는 구체적 지침을 제공했다.
- **인덱스 설계의 의도 명시**: 각 인덱스의 용도를 표로 정리하여 "왜 이 인덱스가 필요한가"를 구현자가 즉시 이해할 수 있다.
- **Phase 구분 명확**: DR-10(문서 수 제한), DR-2 주석 등에서 "MVP에서는 X, Phase 2에서 Y"를 일관되게 구분하고 있다.

## 3. Major (주요 개선사항)

### J-1. id와 slug 이중 컬럼의 실질적 필요성

**문제**: Document 엔티티에서 `id`와 `slug`가 동일한 값(nanoid 8자리)이며, DDL에서도 `id TEXT PRIMARY KEY`와 `slug TEXT NOT NULL UNIQUE`가 별도 컬럼으로 존재한다. 섹션 10에서 "Phase 2 커스텀 slug 지원 시 slug 컬럼을 업데이트하고 id는 유지"라고 설명하지만, 이 설계의 문제점이 충분히 논의되지 않았다.

**구체적 우려사항**:
- Phase 2에서 커스텀 slug를 도입하면 slug가 변경 가능해지므로, 외부 시스템(북마크, 공유 링크)에서 기존 slug로 접근한 경우의 처리 정책이 필요하다.
- MVP 기간 동안 id = slug가 보장되므로, 코드에서 `document.getId()`와 `document.getSlug()`를 혼용할 가능성이 높다. Phase 2 전환 시 리팩토링 범위가 커질 수 있다.

**권장 조치**: 섹션 10의 설계 결정에 다음을 추가한다:
1. Phase 2 커스텀 slug 도입 시 이전 slug의 리다이렉트 정책(301 or 삭제)
2. 코드에서 id와 slug 사용을 구분하는 지침 (URL 라우팅은 slug, 내부 참조는 id)

### J-2. StorageUsage 동시성 제어 전략 부재

**문제**: StorageUsage의 `totalBytes`와 `documentCount`는 문서 생성/삭제/수정/만료 처리 등 여러 경로에서 증감된다. 동시에 같은 사용자가 여러 문서를 생성/삭제하면 lost update가 발생할 수 있다.

**구체적 시나리오**: 사용자가 2개 문서를 거의 동시에 생성할 때, 두 트랜잭션이 각각 `totalBytes`를 읽고 갱신하면 하나의 증가분이 유실된다.

**권장 조치**: 도메인 규칙이나 DDL에 다음 중 하나를 명시한다:
- `UPDATE storage_usage SET total_bytes = total_bytes + ? WHERE user_id = ?` (atomic increment)
- 또는 JPA `@Version` 기반 낙관적 잠금
- 또는 MVP 규모에서는 무시 가능하다는 판단 근거

### J-3. refresh_tokens 엔티티 정의 누락

**문제**: ERD(섹션 7)와 DDL(섹션 8)에 `refresh_tokens` 테이블이 존재하지만, 섹션 2(핵심 엔티티)에 RefreshToken 엔티티 정의가 없다. User, Document, StorageUsage는 상세히 기술되어 있으나 RefreshToken만 누락되었다.

**영향**: backend.md(섹션 6.3)에서 Refresh Token Rotation 로직을 설명하므로 구현에 큰 차질은 없으나, domain.md를 "데이터 모델 원천"으로 참조하는 입장에서 엔티티 정의의 일관성이 깨진다.

**권장 조치**: 섹션 2에 RefreshToken 엔티티를 추가한다. 최소한 필드 정의와 비즈니스 규칙(Rotation, 탈취 감지 시 일괄 무효화)을 명시한다.

### J-4. `documents.user_id` ON DELETE SET NULL의 영향 범위

**문제**: DDL에서 `user_id UUID REFERENCES users(id) ON DELETE SET NULL`로 정의되어 있다. 사용자가 삭제되면 해당 사용자의 모든 문서가 비로그인 문서(`user_id = NULL`)로 변환되지만, `expiresAt`은 `null`인 상태(로그인 사용자 = 영구)로 남아 있게 된다.

**결과**: 삭제된 사용자의 문서가 만료 없이 영구적으로 남아 R2 스토리지를 소비하게 된다. 이는 DR-1("비로그인 문서는 반드시 expiresAt이 설정되어야 한다")과도 모순된다.

**권장 조치**: 다음 중 하나를 선택하여 domain.md에 명시한다:
- `ON DELETE CASCADE`: 사용자 삭제 시 문서도 함께 삭제
- `ON DELETE SET NULL` + 트리거/로직으로 `expiresAt` 자동 설정
- MVP에서 사용자 삭제 기능을 제공하지 않는다고 명시 (가장 간단)

## 4. Minor (사소한 개선사항)

### S-1. 엔티티 관계도(섹션 4)와 ERD(섹션 7)의 역할 중복

섹션 4(엔티티 관계)와 섹션 7(ERD) 모두 mermaid erDiagram을 사용하며, 섹션 4는 개념적 관계, 섹션 7은 물리적 컬럼을 보여준다. 차이가 미미하여 하나로 통합하거나, 섹션 4를 텍스트 기반 관계 설명으로 전환하면 중복감이 줄어든다.

### S-2. Value Objects(섹션 3)에 R2 키 패턴과 Slug 구현 상세 혼재

섹션 3의 이름은 "값 객체 (Value Objects / Enums)"이지만, R2 키 네이밍 패턴, Slug 생성 구현 방법(SecureRandom + 커스텀 알파벳), jnanoid 대안 분석까지 포함되어 있다. 값 객체/Enum 정의와 구현 상세가 섞여 있어 관심사가 분산된다.

**권장 조치**: Enum 정의만 섹션 3에 남기고, R2 키 패턴은 섹션 9(R2 버킷 구조)로, Slug 생성 구현 상세는 backend.md(SlugGenerator 구현)로 이관한다.

### S-3. DDL에 CHECK 제약조건 미사용

DDL에서 `status`, `doc_type`, `plan`, `provider` 등의 컬럼이 `TEXT` 타입으로 정의되어 있으나, `CHECK` 제약조건이 없다. 애플리케이션 레벨에서 검증하더라도, DB 레벨 방어가 추가되면 데이터 무결성이 강화된다.

```sql
-- 예시
status TEXT NOT NULL DEFAULT 'pending'
  CHECK (status IN ('pending', 'active', 'expired', 'deleted')),
```

**권장 조치**: 최소한 `status`와 `doc_type`에는 CHECK 제약조건 추가를 권장한다. Flyway 마이그레이션으로 관리되므로 추후 변경도 용이하다.

### S-4. `idx_refresh_tokens_token` 인덱스와 UNIQUE 제약조건 중복

DDL에서 `refresh_tokens.token`에 `UNIQUE` 제약조건이 걸려 있으므로 PostgreSQL이 자동으로 유니크 인덱스를 생성한다. `idx_refresh_tokens_token` 인덱스를 별도로 생성하면 인덱스가 2개 존재하게 된다.

**권장 조치**: `CREATE INDEX idx_refresh_tokens_token` 라인을 제거하거나, 인덱스 용도 표에 "UNIQUE 제약조건으로 자동 생성됨 — 별도 인덱스 불필요"라고 명시한다.

### S-5. 도메인 이벤트(섹션 5) DocumentUpdated의 contentSize 변경 처리 누락

`DocumentUpdated` 이벤트의 후속 처리에 "R2 파일 덮어쓰기, StorageUsage 업데이트"가 명시되어 있으나, contentSize가 변경될 경우 StorageUsage.totalBytes 조정 방식(이전 크기 차감 + 새 크기 추가)이 기술되지 않았다. backend.md 섹션 7.3에서도 이 부분은 구체적으로 기술되지 않았다.

**권장 조치**: 도메인 이벤트 표 또는 도메인 규칙에 "문서 수정 시 totalBytes는 (기존 contentSize 차감 + 새 contentSize 추가)로 갱신한다"는 규칙을 추가한다.

## 5. 중복 확인

### 기존 식별된 중복 (restructure-review.md 참조)

- **D-1 (R2 버킷 구조)**: domain.md 섹션 9와 backend.md 간 R2 관련 중복. 현재 domain.md는 이미 키 네이밍 + 버킷 구조에 집중하고 접근 방식은 backend.md로 위임하고 있어 개선된 상태이다. R2 접근 방식 상세가 완전히 제거되었는지 확인이 필요하다 — 현재 "R2 접근 방식, SDK 선택, 접속 설정 등의 상세는 backend.md를 참조한다"라는 링크만 남아 있어 적절하다.
- **D-4 (만료 정책)**: product.md의 Free 7일 만료와 domain.md DR-2의 "로그인 사용자 영구"가 다르다. DR-2에 Phase 2 주석이 이미 추가되어 있어 개선된 상태이다.

### 새로 식별된 중복

**없음.** domain.md의 현재 범위(엔티티, 관계, 규칙, ERD, DDL, R2 키 구조)는 backend.md/product.md와 적절히 분담되어 있다.

## 6. 추가 고려사항

### Q-1. 사용자 탈퇴(계정 삭제) 시나리오의 도메인 규칙 부재

현재 도메인 규칙에 사용자 삭제/탈퇴에 대한 정의가 없다. J-4에서 지적한 `ON DELETE SET NULL` 문제와 연결된다. MVP에서 사용자 탈퇴 기능을 제공하지 않더라도, GDPR 등 개인정보 삭제 요청 대응을 위해 최소한의 방침은 도메인 규칙에 포함하는 것이 좋다.

### Q-2. nanoid 8자리 충돌 시 재시도 횟수

backend.md(섹션 14)에서 "최대 3회 재시도"를 명시하지만, domain.md에는 이 규칙이 없다. 충돌 처리는 구현 상세이므로 backend.md에만 있어도 무방하나, DR-5("slug는 시스템 전체에서 유일해야 한다")의 이행 방법으로 교차 참조를 추가하면 추적이 용이하다.

### Q-3. documents 테이블의 `slug` 컬럼 활용도

MVP에서 id = slug이므로 slug 컬럼이 사실상 id의 복사본이다. Phase 2 커스텀 slug 도입 전까지 slug 컬럼은 스토리지와 인덱스를 소비할 뿐 실질적 가치가 없다. MVP DDL에서 slug를 제거하고 Phase 2에서 `ALTER TABLE ADD COLUMN`으로 추가하는 방안도 고려할 수 있다. 다만 이는 섹션 10의 설계 결정("기존 설계 계승")과 상충하므로, 유지하려면 그 비용(UNIQUE 인덱스 추가 스토리지, 코드 복잡도)을 감수하는 근거를 보강한다.
