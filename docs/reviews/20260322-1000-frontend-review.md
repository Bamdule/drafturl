# DraftURL frontend.md 검토 결과

> 검토일: 2026-03-22
> 대상: `docs/architecture/frontend.md`
> 참조: `docs/architecture/backend.md`, `docs/product.md`

---

## 요약

전체적으로 완성도가 높은 프론트엔드 설계 문서다. 페이지 구조, 컴포넌트 계층, API 클라이언트 레이어, 토큰 관리가 구현에 착수하기에 충분한 수준으로 기술되어 있다. backend.md와의 API 경로/인증 플로우도 일관성 있게 맞물려 있다. 다만 치명적 문제 1건(토큰 관리 아키텍처 모순), 주요 개선사항 5건, 사소한 개선사항 4건이 식별되었다.

---

## 잘된 점

1. **역할 경계가 명확하다.** 섹션 2에서 Next.js가 하는 것과 하지 않는 것(DB/R2 직접 접근 X)을 표로 정리하여 혼동 여지를 차단했다. API Routes 없음도 명시적으로 선언하여 구현 시 불필요한 논의를 줄인다.

2. **페이지별 동작이 구체적이다.** 섹션 5에서 각 페이지의 와이어프레임, API 호출 경로, 상태 코드별 분기 처리를 모두 기술하여 구현자가 바로 코드를 작성할 수 있는 수준이다.

3. **backend.md와 API 경로가 일치한다.** `POST /api/v1/documents`, `GET /api/v1/documents/{slug}/view`, `POST /api/v1/auth/oauth2/callback/{provider}` 등 주요 호출 경로가 정확히 매칭된다.

4. **OAuth2 콜백의 state 검증 흐름이 상세하다.** 7단계(생성 -> 쿠키 저장 -> 비교 -> 전달 -> 삭제)를 명확히 기술하여 backend.md의 state 검증 설계와 정합성이 맞는다.

5. **디렉토리 구조가 컴포넌트 역할별로 잘 분리되어 있다.** editor, document, viewer, layout, common으로 나뉘어 있어 관심사 분리가 명확하다.

## C-1: 토큰 저장 위치와 middleware 동작의 모순 [Critical]

**문제**: 섹션 7에서 Access Token을 `httpOnly` 쿠키에 저장한다고 명시하고, Refresh Token의 Path를 `/api/v1/auth/refresh`로 제한한다고 했다. 그런데 이 Path는 Spring Boot API 서버의 경로이지 Next.js 서버의 경로가 아니다.

httpOnly 쿠키는 JavaScript에서 읽을 수 없으므로 클라이언트 컴포넌트에서 `Authorization: Bearer` 헤더를 직접 설정할 수 없다. 섹션 3의 client.ts 설계 원칙 3번("인증이 필요한 요청에 자동으로 Authorization: Bearer 헤더를 추가")과 충돌한다.

또한 Refresh Token의 Path를 Spring Boot 경로로 제한하면, Next.js middleware가 해당 쿠키에 접근할 수 없어 자동 갱신이 불가능하다.

**영향**: 구현 시 토큰 전달 방식을 처음부터 다시 설계해야 할 수 있다.

**제안**: 두 가지 접근 중 하나를 선택하고 문서에 명시해야 한다.
- (A) **쿠키 기반 전달**: Access Token을 httpOnly 쿠키에 저장하고, Next.js middleware 또는 Server Component에서 쿠키를 읽어 Spring Boot에 프록시하는 패턴. 클라이언트 컴포넌트에서 직접 Spring Boot를 호출하는 대신 Next.js Server Action이나 Route Handler를 경유한다. 단, 이 경우 "API Routes 없음" 원칙과 충돌하므로 예외를 명시해야 한다.
- (B) **하이브리드 패턴**: Access Token은 메모리/Zustand에 저장하고(XSS 위험 수용), Refresh Token만 httpOnly 쿠키에 저장한다. 이 경우 Refresh Token Path를 Next.js가 접근 가능한 경로로 변경해야 한다.

## M-1: 문서 목록 API의 응답 필드 매핑 누락 [Major]

**문제**: 대시보드(섹션 5)에서 "사용량: 3개 문서 | 20KB / 5MB"를 표시하는데, 이 데이터를 어떤 API에서 가져오는지 명시되지 않았다. backend.md의 `GET /api/v1/auth/me` 응답에 `storageUsage`가 있지만, frontend.md에서 이 API 호출에 대한 언급이 없다.

**제안**: 대시보드 로딩 시 `GET /api/v1/auth/me`를 호출하여 사용량 정보를 가져온다는 점을 명시하거나, `GET /api/v1/documents` 응답에 사용량 정보를 포함하도록 backend.md와 협의한 결과를 기록한다.

## M-2: 에러 처리 전략이 불충분하다 [Major]

**문제**: client.ts 설계 원칙 6번에서 "구조화된 에러를 throw"한다고 했지만, 각 페이지에서 에러를 어떻게 처리하는지에 대한 전략이 없다. backend.md에는 12가지 에러 코드가 정의되어 있는데, 프론트엔드가 이를 어떻게 사용자에게 표시하는지 기술이 없다.

특히:
- 429 `RATE_LIMIT_EXCEEDED`: 사용자에게 어떤 메시지를 보여주는가? 재시도 안내는?
- 500 `STORAGE_ERROR` / `DATABASE_ERROR`: 일반적인 에러 메시지로 묶는가, 구분하는가?
- 403 `FORBIDDEN`: 대시보드에서 다른 사용자의 문서에 접근했을 때의 UX는?

**제안**: 에러 코드별 사용자 대면 메시지 매핑 표를 추가하거나, 최소한 에러 카테고리(인증 에러 -> 로그인 유도, 권한 에러 -> 접근 불가 안내, 서버 에러 -> 재시도 안내)별 처리 방침을 기술한다.

## M-3: 문서 편집 페이지의 동작 상세가 누락되어 있다 [Major]

**문제**: `app/dashboard/[slug]/edit/page.tsx` 페이지가 라우트 구조에만 존재하고, 섹션 5(주요 페이지 상세)에서 설명이 없다. 메인 페이지(생성)와 편집 페이지(수정)의 차이점이 문서에 기술되지 않았다.

구현 시 다음 질문에 답할 수 없다:
- 편집 페이지 진입 시 `GET /api/v1/documents/{slug}`로 기존 내용을 로드하는가?
- 에디터 UI는 메인 페이지와 동일한 컴포넌트를 재사용하는가?
- "저장" 시 `PUT /api/v1/documents/{slug}`를 호출하는가?
- 수정 후 결과 표시는 모달인가, 토스트인가?

**제안**: 섹션 5에 "문서 편집 페이지" 항목을 추가하여 데이터 로딩, API 호출, UI 동작을 기술한다.

## M-4: 로그인 페이지 동작 상세가 누락되어 있다 [Major]

**문제**: `app/auth/login/page.tsx`가 라우트 구조에 존재하지만 섹션 5에 상세가 없다. OAuth2 로그인 시작 시 state 생성/쿠키 저장/Provider 리다이렉트 흐름이 이 페이지에서 시작되는데, 프론트엔드 측 구현 상세가 기술되지 않았다.

**제안**: 로그인 페이지에서의 동작(state 생성, 쿠키 저장, OAuth2 Provider URL 구성, 리다이렉트)을 기술한다. 특히 state 생성과 쿠키 저장은 보안상 중요한 단계이므로 명시해야 한다.

## M-5: 상태 관리(Zustand) 활용 방안이 누락되어 있다 [Major]

**문제**: 기술 스택에 Zustand를 선택했지만, 어떤 상태를 전역으로 관리하는지에 대한 설명이 전혀 없다. store 파일도 디렉토리 구조에 포함되어 있지 않다.

구현 시 다음을 판단할 수 없다:
- 에디터 상태(content, type, title)를 Zustand로 관리하는가, 컴포넌트 로컬 state로 관리하는가?
- 사용자 인증 상태를 Zustand에 저장하는가?
- 대시보드의 문서 목록 캐싱에 Zustand를 사용하는가?

**제안**: `lib/store/` 또는 `store/` 디렉토리를 추가하고, 주요 store(editorStore, authStore 등)의 상태 구조와 용도를 간략히 기술한다.

## m-1: product.md와 문서 서빙 페이지의 CTA 관련 중복 [Minor]

**문제**: product.md 플로우 A의 7번("공유 URL 페이지 상단 바: 이 문서는 N시간 후 만료됩니다. 나도 만들어보기")과 frontend.md의 문서 서빙 페이지 설명이 부분적으로 겹친다. 다만 frontend.md에서는 상단 바의 CTA 문구를 명시적으로 기술하지 않았다.

**제안**: frontend.md 문서 서빙 페이지에 상단 바 CTA의 구체적인 문구와 조건(비로그인 임시 문서일 때만 표시 등)을 기술하되, product.md를 원천 참조로 링크한다.

## m-2: 만료 문서 처리 방식의 미세한 불일치 [Minor]

**문제**: frontend.md 섹션 5의 문서 서빙 페이지에서 "410: 만료 안내 UI 인라인 렌더링 (리다이렉트 대신 같은 페이지에서 처리하여 slug 정보 유지)"이라고 했다. 동시에 라우트 구조에 `app/expired/page.tsx`가 별도로 존재한다. 만료 문서를 인라인 렌더링한다면 expired 페이지는 어떤 경우에 사용하는가?

**제안**: expired 페이지의 용도를 명확히 한다. 예를 들어 "expired 페이지는 스케줄러가 만료 처리한 후 직접 접근하는 경우에 사용"처럼 사용 시나리오를 구분하거나, 인라인 렌더링으로 통일한다면 expired 라우트를 제거한다.

## m-3: 대시보드의 "[+ 새 문서]" 버튼 동작이 불명확하다 [Minor]

**문제**: 대시보드 와이어프레임에 "[+ 새 문서]" 버튼이 있지만, 클릭 시 동작이 기술되지 않았다. 메인 페이지(`/`)로 이동하는가, 대시보드 내에서 인라인 에디터가 열리는가?

**제안**: "[+ 새 문서] 클릭 시 메인 에디터 페이지(/)로 이동"처럼 한 줄로 명시한다.

## m-4: 환경변수 목록이 없다 [Minor]

**문제**: `NEXT_PUBLIC_API_URL`만 언급되었다. 프론트엔드 배포 시 필요한 전체 환경변수 목록(OAuth Client ID, 서비스 도메인 등)이 없다.

**제안**: 필요한 환경변수를 표로 정리한다. infrastructure.md에 배포 설정이 있다면 그쪽을 참조하되, 프론트엔드 고유 환경변수는 이 문서에 명시하는 것이 좋다.

## 추가 고려사항

1. **접근성(a11y)**: 에디터와 대시보드의 키보드 탐색, 스크린 리더 지원에 대한 언급이 없다. MVP에서 우선순위가 낮더라도 향후 방향성을 한 줄로 남겨두면 좋다.

2. **로딩/스켈레톤 UI**: 문서 서빙 페이지나 대시보드에서 API 응답 대기 중 표시할 로딩 상태(Suspense boundary, skeleton)에 대한 기술이 없다. Next.js App Router의 `loading.tsx` 활용 여부를 명시하면 구현 일관성이 높아진다.

3. **SEO 메타데이터**: 문서 서빙 페이지(`/[slug]`)에서 문서 제목을 `<title>`이나 OG 태그에 반영하는지 여부가 기술되지 않았다. 공유 URL이 SNS에 공유될 때 미리보기 품질에 직접 영향을 준다.

4. **모바일 반응형**: 에디터의 좌우 분할(코드/미리보기) 레이아웃이 모바일에서 어떻게 변환되는지 언급이 없다. Tailwind을 사용하므로 기본적인 반응형은 가능하겠지만, 에디터 UX는 모바일에서 근본적으로 다를 수 있다.

5. **backend.md와의 불필요한 중복은 없다**: frontend.md는 프론트엔드 관점에서 필요한 API 호출 경로만 언급하고, 백엔드 내부 로직(R2 업로드, 2단계 커밋 등)은 다루지 않는다. 문서 간 역할 분리가 적절하다.
