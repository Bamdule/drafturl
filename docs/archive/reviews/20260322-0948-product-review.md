# product.md 검토 결과

> 검토일: 2026-03-22
> 검토 대상: docs/product.md (2026-03-22 최종 수정 버전)
> 참조 문서: architecture/domain.md, architecture/backend.md, market.md

---

## 요약

product.md는 서비스 기능 정의 문서로서 비전, 기능, 플로우, 로드맵, 수익 모델을 체계적으로 다루고 있으며, 이전 검토(mvp-service-design-review.md)에서 지적된 사항들이 대부분 반영되어 완성도가 높다. 주요 개선 포인트는 (1) Team 플랜 마진이 음수인 가격 구조의 리스크, (2) Free 플랜 7일 만료 구현 시점의 모호성, (3) Phase 간 KPI 연결 부재이다. 중복 내용은 market.md와의 경계가 잘 정리되어 있으나, 가격 정책 테이블이 양쪽에서 관리될 소지가 있어 주의가 필요하다.

---

## 잘된 점

1. **MVP 범위가 명확하다.** Phase 2로 이관된 기능의 사유를 테이블로 정리하여 스코프 크리프를 방지하는 좋은 구조이다. 특히 AI 수정 기능을 MVP에서 빼고 "배포 루프 검증"에 집중한 판단이 문서에 명시적으로 근거와 함께 기술되어 있다.

2. **만료 정책의 Phase별 전환이 명시되어 있다.** 5장의 만료 정책 테이블 하단 주석에서 "Free 플랜 7일 만료는 Phase 2에서 구현, MVP에서는 DR-2 그대로"라고 명시한 점이 좋다. domain.md의 DR-2 주석과도 교차 참조가 되어 있다.

3. **AI 비용 추정이 구체적이다.** 토큰 단위 비용 산출, 모델 라우팅 전략(Haiku:Sonnet = 7:3), 플랜별 마진 계산까지 포함하여 수익 모델의 현실성을 검증할 수 있다.

4. **사용자 플로우가 Phase별로 분리되어 있다.** MVP(A, B), Phase 2(C), Phase 3(D, E)로 명확히 구분되어 있어 각 단계에서 무엇을 구현해야 하는지 직관적으로 파악된다.

5. **문서 간 역할 분리가 잘 되어 있다.** 경쟁사 상세 분석은 market.md로, 도메인 규칙 상세는 domain.md로, 기술 스택 상세는 backend.md로 위임하고 교차 참조 링크를 제공한다.

## Critical (치명적 문제)

### C-1. Team 플랜 마진이 음수: 가격 구조 리스크

6장의 "플랜별 예상 마진 계산" 테이블에서 Team 플랜이 **-$2.00/인/월**로 명시되어 있다. 문서에서는 "실사용량이 한도의 30~50%에 그칠 것으로 예상"이라는 가정으로 완화하고 있지만, 이는 위험한 가정이다.

**문제점:**
- Team 플랜은 조직 단위 도입을 목표로 하므로, 파워 유저 비율이 높을 수 있다 (개인 사용자 대비)
- AI 수정 1000회/인/월의 한도를 100% 사용하면 인프라 비용 포함 시 마진이 더 악화된다
- "사용량 모니터링 후 가격 조정 가능"이라는 완화책은 이미 가입한 고객의 가격 인상 반발을 고려하지 않았다

**제안:**
- Team 플랜 AI 수정 한도를 500회/인으로 낮추거나, 가격을 $15/인/월로 조정하여 최악의 경우에도 마진이 양수가 되도록 설계
- 또는 Team 플랜에 "팀 전체 풀(pool)" 방식을 도입하여 (예: 5인 팀 = 3000회/팀) 개별 과사용을 팀 내에서 흡수하는 구조 검토
- 가격 조정 가능성을 언급할 경우, "런칭 프로모션 가격"으로 명시하여 추후 정가 전환의 근거를 미리 마련

## Major (주요 개선사항)

### M-1. Phase 간 KPI 연결이 단절되어 있다

Phase 1, 2, 3 각각에 KPI가 있지만, Phase 간 연결 논리가 없다.

- Phase 1: "일일 문서 생성 수 추이" -> Phase 2의 "월간 활성 문서 수 1,000개"로 이어지는 전환 로직이 없음
- Phase 1의 "가입 전환율 > 5%"가 달성되어야 Phase 2의 "유료 전환율 > 3%"가 의미 있는데, 이 의존성이 명시되지 않음
- Phase 2 -> Phase 3 전환 기준(언제 Phase 3을 시작하는가)이 없음

**제안:** 각 Phase의 "졸업 기준(exit criteria)"을 추가하여, 어떤 KPI가 달성되어야 다음 Phase로 진행하는지 명시. 예: "Phase 1 -> Phase 2 전환 조건: 일일 문서 생성 > 50건 AND 가입 전환율 > 5%"

### M-2. Free 플랜 "문서 3개" 제한의 구현 위치가 불명확

6장에서 Free 플랜의 문서 수를 3개로 제한하지만, 이 제한이 어디에서 적용되는지 불명확하다.

- domain.md의 도메인 규칙(DR-1~DR-9)에 "문서 수 제한" 관련 규칙이 없다
- backend.md의 문서 생성 API에도 플랜별 문서 수 제한 로직이 명시되지 않았다
- StorageUsage 엔티티에 documentCount가 있지만, 이것과 플랜별 한도의 연결이 domain.md에 규칙으로 정의되어 있지 않다

**제안:** domain.md에 "DR-10: Free 플랜 사용자의 활성 문서 수는 3개를 초과할 수 없다" 같은 규칙을 추가하거나, product.md에서 "플랜별 제한은 Phase 2에서 구현"임을 명시

### M-3. 플로우 B에서 "Monaco Editor" 언급은 기능 정의 문서의 범위를 넘는다

플로우 B의 3번 단계에서 "Monaco Editor"라는 구체적인 기술 구현체를 언급한다. 기능 정의 문서에서는 "코드 에디터"나 "텍스트 에디터" 수준의 추상화가 적절하며, 구체적인 라이브러리 선택은 frontend.md에서 다루어야 한다.

**제안:** "Monaco Editor" -> "텍스트 에디터"로 변경

### M-4. Phase 1 주차별 일정(4주)의 현실성 검증이 필요

1주차에 "Spring Boot + Next.js 스캐폴딩, DB 스키마, Flyway 마이그레이션, CI/CD"를 모두 완료하는 것은 1인 개발 기준으로 상당히 빡빡하다. 특히 CI/CD 파이프라인 구축(GitHub Actions + Railway + Vercel)은 초기 설정에 예상보다 시간이 걸린다.

**제안:** 1주차 범위를 "스캐폴딩 + DB 스키마 + 로컬 개발 환경"으로 줄이고, CI/CD는 2주차에 문서 배포 기능과 함께 점진적으로 구축하는 방안 검토. 또는 "1인 개발 기준" vs "팀 개발 기준"을 명시

### M-5. 비로그인 문서의 24시간 만료 알림/가입 유도 메커니즘이 미기술

플로우 A에서 비로그인 사용자가 24시간 만료 URL을 받지만, 만료 전에 어떻게 가입을 유도하는지 구체적인 메커니즘이 없다.

- URL 생성 시 "24시간 후 만료됩니다. 로그인하면 영구 보관" 메시지를 보여주는 것인지?
- 만료 임박 알림(이메일? 브라우저 알림?)이 있는지?
- 비로그인 문서를 로그인 후 "소유권 이전(claim)"하는 플로우가 있는지?

**제안:** 비로그인 -> 로그인 전환의 구체적 UX를 플로우 A에 추가. 최소한 "URL 생성 시 만료 안내 + 로그인 CTA" 정도는 명시

## Minor (사소한 개선사항)

### m-1. 가격 테이블의 용량 단위가 "5MB", "50MB", "100MB"로 되어 있으나 기준이 불명확

문서당 5MB인지(domain.md DR-3), 총 저장 용량인지 구분이 안 된다. domain.md에서는 "문서 내용의 크기는 5MB를 초과할 수 없다"(건당)로 정의하므로, Free 플랜의 "5MB 제한"이 건당 한도와 같아 사실상 제한이 없는 것처럼 보인다. Starter의 50MB, Pro의 100MB가 "총 저장 용량"이라면 명시해야 한다.

**제안:** 가격 테이블의 "5MB/50MB/100MB" 옆에 "(총 저장 용량)" 또는 "(문서당 최대 크기)"를 명시

### m-2. CLI 예시에서 커스텀 slug 사용

플로우 E의 CLI 예시에서 `--title "주간 보고서"`를 지정하면 `weekly-report`라는 slug가 생성되는 것처럼 보이지만, 커스텀 slug는 Phase 2 이관 기능 테이블에 명시되어 있다. Phase 3 플로우에서 커스텀 slug를 사용하는 것은 문제가 없지만, 독자가 혼동할 수 있다.

**제안:** 플로우 E 예시의 URL을 자동 생성 slug 형태(`/xK9mP2nQ`)로 변경하거나, 커스텀 slug가 Phase 2에서 이미 도입된 상태임을 주석으로 명시

### m-3. "데이터 마이그레이션 전략" 내용이 기능 정의 문서보다는 architecture 문서에 적합

Phase 2, Phase 3 하단의 "데이터 마이그레이션 전략" 단락(Flyway, 테이블 추가 등)은 기술 구현 상세에 해당하므로 domain.md 또는 backend.md에 위치하는 것이 더 적절하다.

**제안:** product.md에서는 "기존 데이터와의 하위 호환성을 유지하며 점진적으로 전환한다" 수준의 원칙만 남기고, Flyway/테이블 상세는 domain.md의 "Phase 2 마이그레이션 계획" 섹션으로 이동

### m-4. 변경 이력의 3/22 두 항목이 같은 날짜에 큰 변경을 나열

문서 관리 섹션에서 3/22에 두 건의 변경이 기록되어 있다. 한 건에 통합하거나, 시간을 표기하면 이력 추적에 도움이 된다.

## 추가 고려사항

### 1. market.md와의 가격 정보 중복 관리

현재 market.md 1장에 tiiny.host 가격 테이블이 있고, product.md 6장에 본 서비스 가격 테이블이 있다. 역할이 분리되어 있지만, 추후 가격 변경 시 양쪽을 모두 업데이트해야 하는 상황이 올 수 있다. product.md를 가격의 단일 원천(Single Source of Truth)으로 유지하고, market.md에서는 참조하는 구조가 바람직하다.

### 2. Free 플랜의 AI 수정 10회가 Phase 2 이후 기능인데 가격 테이블에 포함

가격 테이블에 "AI 수정 월 10회"가 Free 플랜에 포함되어 있으나, AI 수정은 Phase 2 기능이다. MVP 시점의 가격 테이블과 Phase 2 이후의 가격 테이블을 구분하거나, "Phase 2부터 적용"이라는 주석을 추가하면 혼동을 줄일 수 있다.

### 3. 국제화(i18n)가 Phase 3에 있으나 한국어/영어 우선순위가 불명확

Phase 3 테이블에 "한국어/영어 우선"이라고 언급되어 있지만, MVP 시점의 기본 UI 언어가 무엇인지 명시되어 있지 않다. 한국어 서비스로 시작하는지, 영어 서비스로 시작하는지에 따라 초기 타겟 시장이 달라진다.

### 4. "발표 모드" (Phase 3)의 범위 정의 필요

Phase 3의 "MD/HTML -> 슬라이드 자동 변환"은 구현 난이도가 높고 별도 서비스 수준의 기능이다. Phase 3 항목들 중 우선순위가 명시되어 있지 않으므로, 실행 시 스코프 크리프의 원인이 될 수 있다.
